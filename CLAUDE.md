## Project

ClaimDesk is a claims-management SaaS module for OMNIVIA, a fictional cross-border e-commerce
company operating in 7 EU countries (France, Allemagne, Espagne, Italie, Belgique, Pays-Bas,
Pologne). It qualifies customer complaints (withdrawal, non-conformity, delivery dispute, billing
error) against simplified EU consumer-law rules and tracks them to resolution across three
personas: end client, processing agent, and management (analytics).

The app is French-language UI/domain content (route labels, form fields, business copy) built on
an English-language technical stack. Keep domain terminology in French to match existing code
(`reclamation`, `dossier`, `recevable`, `qualification`, etc.) — don't translate it.

This project originated in [Lovable](https://lovable.dev) and stays connected to it: pushes to the
connected branch sync back into the Lovable editor. See `AGENTS.md` for the sync constraint (avoid
rewriting published git history — no force-push / rebase / amend of pushed commits).

## Architecture

**Stack**: TanStack Start (SSR React framework, file-based routing via TanStack Router) + Supabase
(Postgres, Auth, RLS) + Tailwind v4 + shadcn/radix UI components. Vite config is provided by
`@lovable.dev/vite-tanstack-config` — do not add TanStack devtools, `tanstackStart()`,
`viteReact()`, `tailwindcss()`, `tsConfigPaths()`, or nitro plugins manually in `vite.config.ts`;
they're already wired in and duplicating them breaks the build. Extend via
`defineConfig({ vite: {...} })` instead.

### Routing (`src/routes/`)

File-based routing — see `src/routes/README.md` for the full convention table. Key points:

- `src/routes/__root.tsx` is the only root layout/shell; never create `src/pages/` or Next/Remix-style directories.
- `src/routeTree.gen.ts` is generated — never hand-edit it.
- `src/routes/_authenticated/route.tsx` is a pathless layout route guarding everything under it: its `beforeLoad` calls `supabase.auth.getUser()` and redirects to `/auth` if unauthenticated. All protected pages (`portail.tsx`, `agent.tsx`, `analytics.tsx`) live under `_authenticated/` and share `AppShell` for chrome (tabs nav + sign-out).
- Role-based destination after login is resolved client-side in `src/routes/auth.tsx` (`destinationFor`) by reading `user_roles`: manager → `/analytics`, agent → `/agent`, otherwise → `/portail`. Route-level access itself is not further gated in the route files — authorization for staff-only server functions is enforced in `assertStaff()` (see below), so a client-role user reaching `/agent` would still be blocked at the data layer.

### Server functions (`src/lib/claims.functions.ts`)

All data mutations/reads go through TanStack Start `createServerFn` handlers (not custom API
routes): `deposerReclamation`, `mesDossiers`, `monProfil`, `tousLesDossiers`,
`majStatutDossier`, `enregistrerCommentaire`, `dossiersAnalytics`. Called from components via
`useServerFn` + React Query. Every handler is wrapped with the `requireSupabaseAuth` middleware;
staff-only handlers additionally call the local `assertStaff()` helper, and `dossiersAnalytics`
further requires the `manager` role specifically.

### Qualification engine (`src/lib/qualification.ts`)

Pure, synchronous, framework-free business logic — `qualifier(input, today?)` implements the
simplified EU consumer-law rules (withdrawal: 14-day window from delivery under 2011/83/EU;
non-conformity: 24-month legal warranty from purchase under (EU) 2019/771, with a 12-month
burden-of-proof split from delivery; delivery/billing disputes always receivable → `instruction`).
This is called synchronously inside `deposerReclamation` before insert — there is no separate
Edge Function for qualification in the current implementation, despite the original spec calling
for one. Also exports the shared domain enums/labels (`PAYS_UE`, `TypeReclamation`, `Statut`,
`LIBELLES_TYPE`, `LIBELLES_STATUT`) used across routes and components. Rules are explicitly
"simplified for MVP, to be refined with a lawyer" — don't over-engineer edge cases here without
being asked.

### Supabase integration (`src/integrations/supabase/`)

This directory is Lovable-managed/auto-generated ("This file is automatically generated. Do not
edit it directly.") — treat changes here cautiously and prefer regenerating via Lovable/Supabase
tooling over hand-editing when possible:

- `client.ts` — browser client (publishable key, persisted session, `localStorage`). Proxy-lazy singleton.
- `client.server.ts` — service-role admin client that bypasses RLS. Server-only; import lazily inside handlers (`await import(...)`), never at top level from route files or `*.functions.ts`, since those ship to the client bundle. Only `.server.ts` modules may import it at top level.
- `auth-middleware.ts` — `requireSupabaseAuth`, a server-side TanStack middleware that reads the `Authorization: Bearer <jwt>` header, validates it via `supabase.auth.getClaims`, and injects `{ supabase, userId, claims }` into handler context. This is what gives server functions an RLS-scoped client per request.
- `auth-attacher.ts` — `attachSupabaseAuth`, the client-side middleware that reads the current session and attaches the bearer token to outgoing server-fn RPCs. Registered globally in `src/start.ts` (`functionMiddleware`) — required, or the browser never sends the token.
- `types.ts` — generated Supabase `Database` types.

Both `client.ts`/`client.server.ts` route around Supabase's new opaque `sb_publishable_`/`sb_secret_`
API keys by stripping any `Authorization: Bearer <key>` header the SDK sets and re-adding the key
via the `apikey` header only — don't reintroduce that Authorization header when touching fetch wiring.

### Data model & RLS (`supabase/migrations/`)

Core tables: `profiles` (1:1 with `auth.users`), `user_roles` (many-to-many user↔`app_role` enum:
`client`/`agent`/`manager`, checked via `SECURITY DEFINER` function `has_role`), `claims` (the
dossier itself — see column list in the migration for the full qualification/status fields,
including auto-generated `numero_dossier` like `CD-2026-1042` via a sequence).
A `handle_new_user` trigger on `auth.users` inserts the `profiles` row and default role from
signup metadata (`raw_user_meta_data`) — this is how `src/routes/auth.tsx`'s sign-up form (which
lets the user pick client/agent/manager) actually assigns a role; there's no admin approval step,
which the code flags as MVP-only (`auth.tsx` comment: production should assign staff roles via an
admin, never at signup).
RLS policies: clients can read/insert only their own claims; agents/managers can read all and
update any (via `has_role`); staff-only server functions add an _additional_ application-level
check (`assertStaff`) on top of RLS, since RLS alone doesn't distinguish agent-only vs
manager-only endpoints (that split — e.g. `dossiersAnalytics` requiring `manager` — is enforced in
`claims.functions.ts`, not in SQL).

### Error handling (`src/lib/error-capture.ts`, `error-page.ts`, `lovable-error-reporting.ts`, `src/server.ts`, `src/start.ts`)

This is a deliberately layered SSR error pipeline — don't simplify it without understanding why
each layer exists:

- `src/start.ts` defines a `errorMiddleware` (server request middleware) that catches thrown errors without a `statusCode` and returns a generated error page instead of letting them surface raw; it also re-registers `createCsrfMiddleware` for server functions (defining `src/start.ts` at all opts out of TanStack Start's automatic CSRF protection, so this file must re-add it explicitly) and wires `attachSupabaseAuth` as global `functionMiddleware`.
- `src/server.ts` wraps the Nitro/TanStack server entry `fetch` and additionally detects the case where h3 has already swallowed a thrown error into a generic `{"unhandled":true,"message":"HTTPError"}` 500 JSON body (which bypasses try/catch) — it recovers the real error via `consumeLastCapturedError()` and substitutes the friendly error page.
- `error-capture.ts` monkey-patches `console.error` (and `window`'s `error`/`unhandledrejection` listeners) to both expand `Error`-like args into full message+stack+cause chains for logs, and cache the last real error for `server.ts` to recover within a 5s TTL.
- `lovable-error-reporting.ts`'s `reportLovableError` forwards errors to Lovable editor's telemetry hooks (`window.__lovableEvents`, `window.__lovableReportRuntimeError`) — a no-op outside the Lovable preview iframe. Called from `__root.tsx`'s root `errorComponent`.

## Conventions

- Path alias `@/*` → `src/*` (see `tsconfig.json`).
- Prettier: 100 print width, double quotes, semicolons, trailing commas everywhere. ESLint enforces Prettier formatting as lint errors; `@typescript-eslint/no-unused-vars` is off.
- TypeScript is strict with several extra strict flags on (`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitReturns`, `noPropertyAccessFromIndexSignature`, etc.) — write code that satisfies these rather than widening types or adding `as any` to route around them.
- Do not import the `server-only` package (Next.js convention) — ESLint blocks it; use a `*.server.ts` filename or `@tanstack/react-start/server-only` instead.
- The `StatutStamp` "official stamp" badge component is the app's signature visual motif for claim status — reuse it rather than inventing new status-display patterns.
